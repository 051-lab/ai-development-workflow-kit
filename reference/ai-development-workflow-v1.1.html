AI Development Workflow

V1.1 · refined operating system for AI-assisted software development

V1.1 preserves the repository-centered architecture of V1 while removing unnecessary ceremony. Project state remains durable and tool-independent, but contained tasks may now use a single-agent Fast Path when a planner-to-builder handoff would add friction without adding meaningful value. P0 hardens operational reliability with evidence authority, stable STATE discipline, atomic Next Actions, and an explicit Operator safety contract — without adding any new machinery.

CORE PRINCIPLE
Stop making AI conversations the home of the project. Make the repository the home of the project.
SEAM PRINCIPLE
Reduce handoffs when the handoff adds no value. Preserve them when planning, risk, or review benefits from separation.

02 — The Repository Is the Source of Truth

Every active project uses the same durable AI state area. V1.1 deliberately keeps the five-file model from V1 rather than collapsing project memory into one large PLAN.md. 

docs/ai/
├── PROJECT.md
├── STATE.md
├── DECISIONS.md
├── REFERENCES.md
└── INBOX.md

PROJECT.md

The stable explanation of the project: purpose, architecture, tech stack, important constraints, repository conventions, supported platforms, and major goals.

STATE.md

The current truth: what is finished, what is in progress, blockers, current branch or milestone, verification status, and the single recommended next action. It opens with a concise Operating Rules block stating evidence authority, atomic Next Action, and the Fast/Deliberate definitions.

DECISIONS.md

Records decisions that should not be repeatedly reopened: architecture choices, intentionally rejected approaches, compatibility decisions, accepted tradeoffs, and important design rationale.

REFERENCES.md

Durable links that would otherwise remain open forever in browser tabs: documentation, GitHub issues, videos, papers, libraries, examples, and research sources — each with a short note explaining why it matters.

INBOX.md

Unprocessed ideas from notebook transcription, Handy dictation, browser research, or sudden thoughts. The inbox is allowed to be messy. The other files are not.

Different information changes at different speeds. Keeping project identity, current state, decisions, references, and unprocessed ideas separate prevents one giant memory file from becoming another source of clutter.

03 — Choose the Lightest Correct Execution Path

The V1.1 workflow does not require a formal planner-to-builder handoff for every task. Before starting, classify the work. Use the lightest path that still protects correctness and project clarity.

Windows / Git / EOL diagnosis

If a tracked file appears unexpectedly modified on Windows, inspect actual Git state before cleanup: git status --short, focused git diff -- <path> and git diff --cached -- <path>, git ls-files --eol -- <path>, and git check-attr -a -- <path>.

Compare git hash-object --path=<path> <path> with git rev-parse HEAD:<path>. The first calculates the blob Git would store after applicable clean/EOL handling; the second returns the blob stored at HEAD. Matching hashes are strong evidence of equivalent stored content even when working-tree representation or status is confusing, but do not authorize discarding files or changing configuration. git update-index --refresh followed by git status is a non-destructive follow-up.

Do not casually change git config --global core.autocrlf or other global settings to fix one file; global configuration changes require explicit authorization. A repository-local .gitattributes may be appropriate only when the project chooses a policy based on supported platforms, generated files, build/tool expectations, and existing conventions. Understand and preserve unexplained changes before any destructive restoration; authorization is required before overwriting them.

07 — Browser Discipline

Browsers remain essential, but their job is research and temporary context. They should not serve as a long-term storage system for project knowledge.

  1. Keep one browser group per active project.
  2. Keep general-purpose tabs separate from project-specific tabs.
  3. When a page becomes important, add it to REFERENCES.md with a one-line explanation.
  4. Close research tabs once their value has been captured.
  5. Do not keep an AI chat open merely because it contains information that has not been written into the repo yet.
  6. Optionally use a dedicated AI/research browser profile if that separation genuinely reduces clutter.

Browser tabs are RAM. REFERENCES.md is storage. A dedicated profile is an optional convenience, not a workflow dependency.

08 — Project Switching and Work-in-Progress Limits

Working on several applications is possible, but only a small number should be considered active at the same time. V1.1 keeps the V1 rule: no more than two active development projects at once.

Before Leaving a Project

1. Update STATE.md
2. Record the single NEXT ACTION
3. Run/record the latest verification state
4. Commit completed work or clearly mark unfinished work
5. Save important browser references
6. Detach the tmux session
7. Close the project browser group

When Returning

1. Attach the project's tmux session
2. Open the project browser group if needed
3. Read PROJECT.md + STATE.md
4. Check git status / current branch
5. Classify the next task: Fast Path or Deliberate Path
6. Continue the recorded NEXT ACTION

11 — Evidence Authority, State Discipline, and the Operator Contract

P0 hardens the V1.1 workflow for operational reliability without adding machinery: no daemon, database, service, or orchestration layer. Repository evidence itself becomes the referee when documentation and execution disagree.

Evidence hierarchy

When repository, Git, remote, CI, test, or other authoritative execution evidence conflicts with stale STATE.md content, verified evidence wins. The mismatch must still be reported, and STATE.md may be corrected during an appropriate bounded state/work update. There is no automatic correction loop; mismatches are reported rather than chased with self-invalidating commits.

Stable STATE discipline

Do not create a STATE-only commit merely to chase metadata changed by the previous STATE commit. A STATE-only commit may be appropriate at a meaningful project or handoff boundary when it records stable operational truth that remains true after the commit. Prefer durable facts over self-invalidating details such as exact current HEAD hashes. STATE.md must not become a workflow manual.

Atomic Next Action

Exactly ONE Next Action. An atomic Next Action represents one operation/outcome, with one independently verifiable completion state, and never bundles separate lifecycle operations with "and".

AtomicCompound (not allowed)
Push branch to origin.Push branch and open a PR.
Open PR to main.Fix dependencies and run the complete validation suite.
Inspect the failing CI job.Review, fix, commit, and merge.
Repair the local Node environment.—

Remaining work stays in planning context, Blockers / Risks, or INBOX — never bundled into the Next Action.

Roles: Human, Planner/Reviewer, Operator

Roles are tool-agnostic; none is bound to any named AI product or model.

RoleResponsibility
HUMANChooses goals, sets priorities, approves meaningful decisions.
PLANNER / REVIEWERReasons about architecture and scope, reviews repository evidence, identifies consequential decisions.
OPERATORRuns repository/terminal commands, reads repository evidence, performs bounded edits, runs verification, reviews actual diffs, reports evidence, updates durable state when appropriate.

The Operator may be the same agent as the builder during a Fast Path task.

Operator safety boundary

Bounded normal operations — read-only Git inspection, reading files, bounded edits, running tests/builds/checks, reviewed staging, and ordinary commits or feature-branch pushes when explicitly in task scope — need no extra authorization. Explicit authorization is required for destructive operations:

  • git reset --hard / git clean
  • Force push, branch deletion, history rewriting
  • Global Git configuration changes
  • Discarding unexplained changes; destructive broad file deletion
  • Bypassing failed validation
The Operator must STOP and report unexpected repository state rather than improvising through it. Authorization is not granted automatically merely because a destructive operation might solve the immediate problem.

Independent review

Use prompts/REVIEW.md for an independent assessment grounded in the actual diff, acceptance criteria, recorded constraints and decisions, and verification evidence. The reviewer reconciles STATE.md against authoritative repository, Git, remote, CI, and test evidence; checks the single atomic Next Action and stable STATE discipline; and reports the smallest evidence-backed correction. Routine stale STATE is reported but does not automatically require FIX REQUIRED when scope and safety remain correct. Material scope, safety, acceptance, or validation conflicts may require it. Verdicts remain PASS, PASS WITH FOLLOW-UP, and FIX REQUIRED.

Resuming must work days later with only the repository. Read PROJECT.md and STATE.md, inspect current repository evidence, decide whether STATE.md is current or stale, treat verified evidence as authoritative, and report mismatches. Do not create a STATE-only correction commit merely because STATE describes an operation evidence shows is already complete. Identify exactly ONE atomic Next Action and classify it as Fast Path or Deliberate Path.

V1.1 OUTCOME
V1.1 keeps the durability of V1 while reducing unnecessary handoffs. The repository remains the project memory. Notebook and Handy capture thoughts at the appropriate level of effort. ChatGPT handles deep planning when it is actually useful. OpenCode handles routine local work and can plan + build contained tasks in one session. Review remains available when risk justifies it. The workflow becomes lighter without becoming looser.
